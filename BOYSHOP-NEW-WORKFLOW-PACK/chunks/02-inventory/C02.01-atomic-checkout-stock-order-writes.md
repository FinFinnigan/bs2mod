# C02.01 — Atomic checkout stock/order writes

## Routing
Routing: run mandatory agent-aware preflight before execution.
Run mandatory `ROUTING-PREFLIGHT.md` immediately before execution.
Do not hardcode a named agent here.
Capability preference: implementation (TypeScript/Drizzle backend correctness).

## Outcome
`DrizzleOrderRepository.create()` persists the `variants.stock` decrement together with the order, order items, and address as **one all-or-nothing database operation**. A write failure at any step leaves both stock and orders untouched, and concurrent duplicate idempotency-key requests produce exactly one order and exactly one stock decrement. The in-memory repository keeps matching observable behavior.

## Scope
Exactly this concern and directly related files:

- `src/lib/backend/repositories/drizzle/order.ts` — restructure `create()` (~lines 22–108: stock pre-check, conditional decrement, manual compensation on later failure, then INSERT orders / order_items / addresses) into one atomic operation; `getByIdempotencyKey()` ~line 117.
- `src/lib/backend/db/client.ts` — the Drizzle client instantiation; switch the driver import to a transaction-capable entry point from the **already installed** `@neondatabase/serverless` package (e.g. `drizzle-orm/neon-serverless` with `Pool`, `drizzle-orm@^0.45.2` supports `db.transaction`) only if that is the smallest way to obtain `db.transaction`. This chunk authorizes **no new npm dependency** — if a working transaction turns out to require one, STOP and request authorization.
- `src/lib/backend/services/checkout.ts` — the idempotency pre-check (~line 60 `getByIdempotencyKey(input.idempotencyKey)`) runs before `create()` and is not concurrency-safe alone; adjust the smallest necessary surface (keep the early return, rely on the transaction's re-check plus the unique key for races).
- `src/lib/backend/repositories/interfaces.ts` — only if the create contract must change (prefer not to).
- `src/lib/backend/repositories/memory/index.ts` — keep observable parity (`create`, `getByIdempotencyKey` ~line 428).
- New tiny unit-level target tests in the existing Vitest layout for the atomic behavior (DB-backed proof belongs to C02.02).

Evidence: recon verified **no** `db.transaction(...)` / `db.batch(...)` usage anywhere in `src/`. The live Drizzle order repository currently decrements stock before writing order/items/address with manual compensation, so a later failure can reduce stock without a complete order; the idempotency check at `checkout.ts:60` races under concurrency (two same-key requests can both pass it).

## Implementation
Smallest safe change: wrap the whole create path in one `db.transaction` that (1) re-checks the idempotency key inside the transaction, (2) performs a conditional stock decrement (`UPDATE ... SET stock = stock - <n>` with the stock-availability guard, or the repo's existing conditional form) that must affect exactly one row else abort with the stock-conflict error the service already maps to HTTP 409, and (3) inserts order, items, and address. If the transaction aborts — including a unique-key violation from a concurrent duplicate idempotency request — nothing is persisted; keep the service's existing conflict/duplicate handling intact. No unrelated refactors, no schema changes, no new dependencies.
