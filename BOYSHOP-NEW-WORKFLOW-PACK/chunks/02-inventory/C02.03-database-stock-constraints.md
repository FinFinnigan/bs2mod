# C02.03 — Database non-negative stock constraint

## Routing
Routing: run mandatory agent-aware preflight before execution.
Run mandatory `ROUTING-PREFLIGHT.md` immediately before execution.
Do not hardcode a named agent here.
Capability preference: implementation (Drizzle schema + migration authoring).

## Outcome
`variants.stock` is constrained at the database level to be non-negative via a CHECK constraint, delivered as the repository's next Drizzle migration (`0006_*`) authored in `schema.ts` and applied/verified on an **isolated test database**. Applying it to the production-candidate Neon `boyshop/main` is a separate CEO-gated action and is **not** part of this chunk.

## Scope
- `src/lib/backend/db/schema.ts` — variants table: add a named CHECK constraint (e.g. `variants_stock_nonnegative`) enforcing `stock >= 0`, using the installed Drizzle schema API (`check(...)` with `sql`) — confirm support in the installed `drizzle-orm@^0.45.2` at execution.
- `src/lib/backend/db/migrations/` — generate the new migration via `npm run db:generate` (`drizzle-kit generate`, config at repo-root `drizzle.config.ts`); existing migrations 0000–0005 + `meta/_journal.json` stay untouched.
- Isolated test database (same rule as C02.02 — local Postgres or Neon test branch; never live `boyshop/main`).
- One small verification: a DB-backed rejection check recorded as evidence (only if the existing Vitest layout already has a DB-backed precedent; otherwise a scripted SQL check is sufficient evidence).

## Out of scope
- Applying the migration to the production-candidate database (`boyshop/main`): requires the full C01.08 prerequisite chain (restore snapshot, separate test branch, source/database schema verification, branch test) plus a separate explicit CEO migration approval — report as a pending gate, do not run it.
- Altering or removing the `products.inStock` column (C02.04 territory, and a further schema change).
- Checkout/repository code and any new npm dependencies.

## Implementation
Smallest safe change: add the CHECK in `schema.ts`, run `npm run db:generate` to produce migration `0006_*` under `src/lib/backend/db/migrations/`, then apply it to an isolated test database (database URL from environment, never committed) and verify the database rejects a negative-stock insert while accepting `stock = 0`.

## Verification
- `npm run db:generate` produces a new migration containing the CHECK; `git diff` shows only `schema.ts` + the new migration files.
- `INSERT ... variants.stock = -1` fails on the test database; `stock = 0` succeeds.
- `npm run typecheck` passes; existing suite unchanged and green (`npm test`).
- Evidence recorded: migration name, test database used, and the rejected-insert error.
